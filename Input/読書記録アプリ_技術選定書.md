# 読書記録アプリ 技術選定書

## 1. 目的

本書は「読書記録アプリ」の開発に使用する技術を定義する。

以下の要件を満たすことを目的とする。

- iPhoneアプリとしてApp Storeで公開できること
- Windows環境で開発できること
- バーコードから書籍を登録できること
- 書籍検索ができること
- 読書記録をクラウドに保存できること
- 機種変更時に読書データを引き継げること
- 個人開発で無理なく保守・拡張できること

# 3. アプリフレームワーク

## 3.1 React Native

### 採用

**React Native**

### 採用理由

今回の開発者がReact / TypeScriptを利用できるため、既存スキルを活用できる。

また、本アプリは以下のような一般的なモバイルアプリ機能が中心である。

- 一覧表示
- フォーム
- API通信
- カメラ
- バーコード読み取り
- 画像表示
- データ登録・編集・削除

これらはReact Nativeと相性が良い。

### SwiftUIを採用しない理由

SwiftUIはiOSアプリ開発として非常に優れた選択肢だが、開発環境としてmacOS + Xcodeが必要になる。

今回の開発環境はWindowsであるため、React Native + Expoを採用する。

# 4. Expo

## 4.1 採用

**Expo**

React Nativeプロジェクトの開発基盤としてExpoを利用する。

# 9. 認証

## 9.1 Supabase Auth

### 採用

**Supabase Auth**

### 目的

ユーザーの読書記録をアカウントに紐付ける。

これにより、機種変更時に同じアカウントでログインすることでデータを復元できる。

### 認証方式

第一候補：

**Sign in with Apple**

将来的に以下を追加する可能性がある。

- Google
- メールアドレス

MVPでは認証方式を必要以上に増やさない。

---

# 10. データアクセス制御

## 10.1 Supabase Row Level Security

### 採用

**RLS（Row Level Security）**

### 目的

ユーザーが自分の読書データだけを参照・変更できるようにする。

概念：

```text
User A
  ↓
User AのReadingRecordのみ参照可能

User B
  ↓
User BのReadingRecordのみ参照可能
```

アプリ側の制御だけに依存せず、DB側でもアクセス制御を行う。

# 12. 読書ステータス

DB上では表示名ではなく固定値を利用する。

```text
to_read
finished
```

アプリ上では、

```text
to_read  →  これから
finished →  読了
```

として表示する。

「読書中」は使用しない。

# 14. 書籍情報API

## 14.1 第一候補：OpenBD

日本の書籍を中心としたアプリであるため、OpenBDを第一候補として評価する。

主な評価項目：

- ISBN検索
- 日本語書籍への対応
- 書誌情報
- 表紙画像
- API利用条件
- 安定性

### フォールバック候補

必要に応じて以下を検討する。

- Google Books API
- 国立国会図書館系API
- 楽天ブックス系API

### API設計方針

書籍APIのレスポンスをそのままアプリ内部で利用せず、アプリ用のBookモデルに変換する。

```text
書籍API
   ↓
API Response
   ↓
Mapper
   ↓
Book
```

これにより、将来的に書籍APIを変更しやすくする。

# 25. セキュリティ方針

最低限以下を実施する。

- Supabase Authを利用
- RLSを有効化
- user_idによるデータ分離
- Supabaseの秘密鍵をアプリに直接埋め込まない
- 公開可能なキーと秘密鍵を区別する
- APIキーをGitHubへコミットしない
- 環境変数を利用する

# 27. 技術選定の基本方針

今回のアプリでは「最先端の技術を使うこと」よりも、

1. Windowsで開発できる
2. iPhoneアプリとして公開できる
3. 個人開発で扱いやすい
4. 将来の機種変更に対応できる
5. 将来的な機能追加に対応できる
6. 既存のReact / TypeScript / Supabaseの知識を活かせる

ことを優先する。
